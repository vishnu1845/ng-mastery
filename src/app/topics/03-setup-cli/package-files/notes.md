## Definition

`package.json` declares your dependencies with flexible version ranges. `package-lock.json` locks the exact versions actually installed, including nested ones — so everyone on the team and CI get identical builds.

## Example (from a new v22 app)

```json
{
  "name": "my-app",
  "scripts": {
    "start": "ng serve",
    "build": "ng build",
    "test": "ng test"
  },
  "dependencies": {
    "@angular/core": "^22.2.0",
    "rxjs": "~7.8.0"
  },
  "devDependencies": {
    "@angular/cli": "^22.2.3",
    "typescript": "~6.0.2"
  }
}
```

## Comparison

|                     | package.json                    | package-lock.json              |
| ------------------- | ------------------------------- | ------------------------------ |
| Purpose             | Declares dependencies & scripts | Locks exact installed versions |
| Version format      | Flexible (`^`, `~`)             | Exact (`22.2.3`)               |
| Edited by           | Developer                       | Auto-generated by npm          |
| Covers nested deps? | ❌                              | ✅                             |
| Commit to git?      | ✅ Yes                          | ✅ Yes                         |

## Key points

- **`^22.2.0`** → allows minor + patch updates (`22.x.x`). **`~7.8.0`** → allows patch updates only (`7.8.x`).
- **`dependencies`** → needed by the app at runtime. **`devDependencies`** → needed only to build & test.
- **`npm install`** → installs & may update the lock file. **`npm ci`** → clean install **exactly** from the lock file (used in CI).

## Say it like this

"package.json is the heart of the project. It lists our dependencies with flexible ranges, like caret and tilde, and our scripts, like `npm start` running `ng serve`. But flexible ranges mean two machines could install different versions, so package-lock.json locks the exact versions, including nested packages. That's why we commit both, and in CI we use `npm ci` to install exactly what's in the lock file."
